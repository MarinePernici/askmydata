# ADR-0004 — Validate Every Generated SQL Query Before Execution

## Status

Accepted

**Date:** 2026-07-14

---

# Context

AskMyData enables users to query external databases using natural language.

The application relies on a Large Language Model (LLM) to generate SQL statements from user requests.

Although modern LLMs produce increasingly accurate SQL, their output cannot be considered inherently safe or correct.

Potential risks include:

- generation of invalid SQL;
- hallucinated tables or columns;
- queries outside the selected Catalog Scope;
- destructive SQL statements;
- excessive resource consumption;
- unintended disclosure of sensitive information.

Prompt instructions alone cannot guarantee safe behavior.

The application therefore requires independent validation before executing any generated SQL.

---

# Decision

Every SQL statement generated by the Query Engine must be validated before execution.

The Query Validator is a mandatory stage of the execution pipeline.

No generated SQL may reach the external database unless it has successfully passed all validation checks.

Validation is implemented independently of the LLM and does not rely on prompt engineering alone.

Execution is performed exclusively through a read-only database connection.

---

# Rationale

The LLM is treated as an intelligent assistant rather than a trusted execution engine.

Separating SQL generation from SQL validation provides multiple benefits:

- improved security;
- deterministic validation rules;
- easier testing;
- better observability;
- clear separation of responsibilities.

Validation also ensures that infrastructure-level safeguards complement application-level safeguards.

The external database remains protected even if the generated SQL is incorrect or unexpected.

---

# Validation Strategy

The validation pipeline combines several independent controls.

## SQL Structure

The generated statement must:

- be syntactically valid;
- contain a single statement;
- be supported by the selected connector.

---

## Read-Only Enforcement

Only read-only SQL statements are permitted.

Examples include:

- SELECT
- WITH (read-only Common Table Expressions)

Statements such as the following are rejected:

- INSERT
- UPDATE
- DELETE
- MERGE
- TRUNCATE
- ALTER
- DROP
- CREATE
- GRANT
- REVOKE

---

## Catalog Scope Validation

Referenced objects must belong to the active Catalog Scope.

Queries referencing hidden or excluded schemas, tables or columns are rejected.

---

## Database Permissions

The external database connection must use a dedicated read-only account.

Application-level validation complements, but never replaces, database-level security.

---

## Execution Limits

Validated queries remain subject to execution constraints.

Examples include:

- statement timeout;
- maximum number of returned rows;
- connector-specific limits.

---

# Consequences

## Positive

- Improved application security.
- Reduced risk of accidental data modification.
- Better protection against LLM hallucinations.
- Clear separation between generation and execution.
- Easier testing of validation rules.
- Stronger operational guarantees.
- Better auditability.

## Negative

- Additional implementation effort.
- Slightly increased execution latency.
- Validation rules must evolve alongside supported SQL features.

---

# Alternatives Considered

## Execute Generated SQL Directly

The generated SQL could be executed immediately after generation.

### Advantages

- Simpler implementation.
- Lower latency.

### Reasons for rejection

This approach would expose the application to unacceptable risks.

Prompt engineering alone cannot reliably prevent:

- destructive statements;
- invalid SQL;
- access outside the permitted scope;
- excessive resource consumption.

---

## Prompt-Based Restrictions Only

The prompt could explicitly instruct the LLM to generate safe SQL.

### Advantages

- Very low implementation cost.
- No validation component.

### Reasons for rejection

Prompt instructions are probabilistic rather than deterministic.

They are useful for improving generation quality but must never be considered a security mechanism.

---

# Future Evolution

Future versions of the Query Validator may introduce additional controls, including:

- SQL parsing through dedicated parsers;
- connector-specific validation rules;
- query complexity estimation;
- cost estimation;
- automatic query rewriting;
- policy-based access control;
- row-level security integration;
- query approval workflows.

These enhancements should strengthen validation without changing the fundamental principle that every generated query must be validated before execution.
